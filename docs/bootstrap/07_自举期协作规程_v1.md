## 2. 交接的基本顺序

```text
架构师出规格 → 本机操作员入库并推送 → 测试员写测试 → 本机操作员合并锁定
→ 开发员写代码并发布 PR → 审查员审查 → 本机操作员合并 → 本机实测
```

**三条铁律**：

1. **上游推送完成之前，不让下游开工**。例：规格还没推送到 GitHub，测试员就读不到。判断办法：在 GitHub 网页上能看到对应文件，或本机操作员回报 `up to date with 'origin/main'`。
2. **发指令前核对对象**：每段指令开头都写明"你是某某岗位"，发之前看一眼会话名称对不对。发错会话时，**不返工，如实登记**（先例：自举记录第 14 行更正）。
3. **云端开发员交件后，必须在任务页面点"创建 PR"发布**，否则代码只留在云端容器里。PR 只用来阅读，**永远不在 GitHub 上点合并**（D-206②）。

## 4. 固定合并模板（无阻断时使用）

```text
新任务：合并 <分支名>（报告结论：无阻断）。
在 D:\Tianlong\TL-L0-Guide\ 内：
1. git fetch origin；git switch -c <分支名> origin/<分支名>。
2. 运行 python -m unittest discover -s tests/acceptance/seg1，报告总数、通过、失败、出错、跳过（附跳过原因）。
   结果与报告不一致就停下，不要合并。
3. 确认改动范围：git diff --stat origin/main...<分支名>，只应包含 <允许改动的路径>；超出就停下。
4. git switch main；git merge --ff-only <分支名>（不能快进就停下）。
5. 在 docs/bootstrap/00_自举记录.md 表格末尾追加一行（只追加）：
   | <下一个序号> | <日期> | <一句话事项> | 通过（无阻断，直接合并） | <依据文件或报告> |
6. git add -A；git commit -m "<提交说明>"；git push；删除远端和本地的 <分支名>。
完成后给出：第 2 步测试摘要、git log --oneline -3、git status。
```

## 5. 审查员复审模板（开发员交件后）

```text
你是审查员（REV），本次为复审。只读、不改：不提交、不推送、不修改任何文件。
审查对象：分支 <分支名> 相对 origin/main 的全部改动（git fetch origin 后用
git diff origin/main...origin/<分支名>；以 origin/main 为基准，不要用本地 main）。
【依据】docs/spec/ 下现行接口规格（后加的节优先于前文）；docs/bootstrap/ 下历次审查报告；
锁定用例 tests/acceptance/；开发员交接卡（在该分支上）。
【重点】① 上一轮阻断问题是否消除，逐条给出代码位置与验证方法，能实测的在临时目录实测；
② 本轮新裁定是否逐条落实，有无新的越权写入、外部程序调用、网络访问或路径穿越；
③ 开发员对待定问题的假设是否合理；
④ 分别用 python3.10 和默认 Python 运行全部用例并报告；确认没有改动 tests/、docs/spec/、src/templates/。
【输出】直接在回复中给出：结论（通过／有条件通过／不通过）；阻断问题（行号、问题、建议）；
非阻断问题；能否允许本机运行或合并的明确意见。
```

## 6. 本机运行的前提

- 运行环境中没有任何 `TL_` 开头的环境变量（PowerShell：`Get-ChildItem Env:TL_*` 应为空）。
- **本机验收或冒烟前，先移走业务仓库**：确认 `D:\Tianlong\qiaofeng-bid` 干净、与远端一致后删除，测完再从 GitHub 克隆回来，并执行 `git config core.longpaths true`、`git config merge.ff only`（D-206⑥）。
- 规程包代码首次在本机运行，须审查员明确给出"允许本机运行"（D-205③(c) 先审后执行）。
