## 1. 范围

段1 只做**记录层**：四种记录的格式，以及一个命令行工具 `tl` 的五个子命令。钩子、护栏、导引技能不在段1（分属段2、段3）。

| 子命令 | 干什么 | 谁来运行 | 会写到哪里 |
| :-- | :-- | :-- | :-- |
| `tl status` | 用中文列出任务的进度、待签包和签字情况 | Fred 或 AI | 只读 |
| `tl pack` | 生成待签包清单，算出指纹码 | 导引技能（AI） | 仓库内 `.tianlong/work/` |
| `tl sign` | 核对文件未变后，往签字记录追加一行 | AI 请求运行，**Fred 在批准框点"仅本次批准"**（做法 A） | 仓库外签字目录 |
| `tl verify` | 核对某个包是否已有效签字、签后文件有没有被改 | 检查脚本、导引技能 | 只读 |
| `tl check` | 核对进度卡、假设日志、交接卡字段是否齐全合法 | 检查脚本、导引技能 | 只读 |

## 2. 运行环境与通用约定

| 项 | 约定 |
| :-- | :-- |
| 语言 | Python 3（3.10 及以上），**只用标准库** |
| 运行方式 | 在项目仓库根目录下运行 `python <规程包路径>/src/bin/tl.py <子命令> …`。规程包装入项目后，路径为 `.tianlong/pkg/src/bin/tl.py`；在模板仓库自测时为 `src/bin/tl.py` |
| 仓库根 | 以 `git rev-parse --show-toplevel` 为准；不在 git 仓库内即报错 |
| 仓库名 | 仓库根文件夹名，如 `qiaofeng-bid` |
| 签字目录 | 默认 `C:\TianlongSign\<仓库名>\signatures.jsonl`；环境变量 `TL_SIGN_DIR` 可以改签字根目录（供测试使用）〔本规格新增〕 |
| 时间 | ISO 8601、带时区，如 `2026-10-03T21:14:05+08:00`；环境变量 `TL_NOW` 可以固定当前时间（供测试使用）〔本规格新增〕 |
| 文件编码 | UTF-8、无 BOM、换行 LF（仓库 `.gitattributes` 已统一） |
| JSON 键名 | 全小写英文、下划线连接 |
| 代号取值 | 沿用正本代号原样书写，如 `CH-FEAT`、`S1-SPD`、`COND-UI`；小写规则只管文件名、目录名、任务编号与包编号 |
| 输出 | 默认输出中文，供人看；加 `--json` 时标准输出**整体是一份合法 JSON**，不夹任何提示行（结构段3 再定）〔v0.2〕。程序启动即把标准输出、标准错误设为 UTF-8，保证 Windows 控制台下中文不乱码〔v0.2〕 |

**退出码**（五个子命令共用）：

| 码 | 含义 |
| :-: | :-- |
| 0 | 成功，或核对通过 |
| 1 | 用法错误：参数缺失或不合法、包编号格式不合法或包不存在、不在 git 仓库内〔v0.2〕 |
| 2 | 记录字段不合法（`check` 的发现，或读入的记录本身有误） |
| 3 | 文件指纹不符：待签包里的文件被改过或已不存在，签字作废 |
| 4 | 未签字、已退回，或签字无效 |
| 5 | 签字记录本身损坏：链式校验失败、格式错误或同一个包出现重复签字 |

## 4. 四种记录

字段含义、取值和依据以段1 设计 v0.5 第 2～4 节为准，本节只补**机器层面的约定**。

### 4.1 进度卡 `.tianlong/work/<任务编号>/progress.json`

- 必填字段：`task_id`、`channel`、`baseline_commit`、`current_step`、`conditions`、`token_holder`、`steps`。
- 〔v0.2〕格式：`baseline_commit` 为 7～40 位小写十六进制；`current_step` 形如 `S0-INI`～`S7-…`（`S` ＋ 一位数字 ＋ 连字符 ＋ 大写字母）；`token_holder` 须含 `role` 与 `since` 两项；`task_id` 须与所在目录名一致。
- `channel` 取值：`CH-FEAT`、`CH-FIX`、`CH-MINOR`。
- `conditions[].readiness` 取值：`就绪`、`适用未就绪`。取"适用未就绪"时，`exception_ref` 必填。
- `steps[].result` 取值：`成功`、`失败`、`结果不明`。

### 4.2 待签包清单 `.tianlong/work/<任务编号>/packages/<包编号>.json`

- 字段：`package_id`、`doc_type`、`task_id`、`step`、`summary`、`created_at`、`created_by`、`files[]`（`path`、`sha256`、`role`）、`manifest_sha256`、`fingerprint_code`。
- `files[].path`：相对仓库根的路径，用正斜杠。**不得**指向仓库之外，也不得指向**任何任务**的 `packages/` 目录〔v0.2〕；按路径字母序排列。`role` 取 `正文` 或 `附件`，正文恰好一个。
- **清单指纹的算法**：取清单内容，去掉 `manifest_sha256` 和 `fingerprint_code` 两个字段，按"键名排序、紧凑格式（分隔符为逗号和冒号，无空格）、UTF-8、非 ASCII 字符不转义"序列化，对结果算 SHA-256，得到 `manifest_sha256`（小写十六进制）。
- `fingerprint_code`：`manifest_sha256` 的前 8 位。
- 文件指纹按文件**原始字节**计算，不做换行转换；排序按路径字符串逐字符比较〔v0.2〕。
- 清单生成后不再改动；清单文件名须与其中的 `package_id` 一致〔v0.2〕。

### 4.3 签字记录 `<签字目录>/<仓库名>/signatures.jsonl`

每行一个 JSON 对象，只追加、不改旧行。字段：

| 字段 | 说明 |
| :-- | :-- |
| `package_id`、`decision`、`fingerprint_code`、`reason`、`signed_at`、`signer` | 同段1 设计 v0.5 §3.2。`decision` 取 `已确认` 或 `退回`；`signer` 固定为 `APR:Fred` |
| `prev_sha256` | **〔本规格新增〕链式校验**：上一行原文（不含行尾换行）的 SHA-256；第一行填 64 个 `0` |

**同一个包只能签一次**〔本规格新增〕：已确认或已退回的包，不能再签；退回后要重新生成一个新序号的包再签。

### 4.4 假设日志 `.tianlong/work/<任务编号>/assumptions.jsonl`

- 每行一条，字段见段1 设计 §4。〔v0.2〕必填：`id`、`step`、`decision`、`reason`、`cost`、`recorded_by`、`recorded_at`；`cost` 为"低"时 `low_reason` 必填；`task_item`、`files`、`s6_route` 选填。
- `cost` 取 `低`、`中`、`高`，缺省为 `中`。
- 取"低"时，`low_reason` 必须是以下四个固定值之一：`纯命名`、`纯格式`、`不涉状态`、`不涉接口数据与权限`。

## 5. 子命令细则

### 5.1 `tl status [--task <任务编号>] [--json]`

- 不带 `--task`：列出 `.tianlong/work/` 下所有任务，每个任务一行：当前步骤、通道、令牌持有者、有几个待签包未签。
- 带 `--task`：给出该任务的完整中文摘要。包括进度卡各栏；每个待签包的包编号、文书类型、指纹码、签字状态（未签／已确认／退回／**签后文件已变**）；以及包内的文件清单。
- 退出码：0；进度卡不合法时为 2，并列出问题。

### 5.2 `tl pack --task <任务编号> --doc <文书代码> --step <步骤代号> --main <正文路径> [--attach <附件路径> …] --summary "<一句话摘要>" [--json]`

- 核对各项参数合法、文件都存在且在仓库内、**该任务的进度卡已存在**、`--step` 符合 4.1 的步骤代号格式〔v0.2〕，然后算出每个文件的指纹，写入清单；`created_by` 写非空字符串，缺省为 `tl`〔v0.2〕。
- 屏幕输出推送行：`<包编号>｜<文书类型>｜指纹码 <8 位>｜<摘要>`。`--json` 时输出完整清单。
- 退出码：0；参数不合法为 1；文件不存在或在仓库外为 1。

### 5.3 `tl sign <包编号> <确认|退回> [--reason "<理由>"] [--json]`

决定也接受英文写法：`confirm`、`reject`。

执行顺序：
1. 读取清单，**重新计算**每个文件的指纹和清单指纹，任何一项不符 → 退出码 3，不写入；
2. 该包已有签字 → 退出码 5，不写入；
3. 决定为"退回"但没给理由（空串或只有空白也算没给）→ 退出码 1，不写入；
4. 签字目录不存在 → 自动创建 `<仓库名>` 子目录；签字根目录本身不存在 → 退出码 1；
5. 校验签字记录现有各行的链条，失败 → 退出码 5，不写入；
6. 追加一行，屏幕回显写入的内容。

**说明**：本命令本身无法分辨是谁在运行它。"只有 Fred 能签"靠的是做法 A：签字目录在 Codex 沙箱之外，AI 请求运行本命令时必然弹出批准框，框只有 Fred 能点；Claude Code 岗位在云端，接触不到签字目录（D-206①）。

### 5.4 `tl verify <包编号> [--json]` ／ `tl verify --task <任务编号> [--json]`

对每个包依次核对：
- 签字记录的链条完好；有任何一行不是合法 JSON 也算损坏（否则 5）；
- **重新计算清单指纹**，与清单里的 `manifest_sha256` 一致（否则 3）〔v0.2〕；
- 该包有且只有一条签字（没有，含签字记录文件尚不存在 → 4；多于一条 → 5）；
- 决定为"已确认"（退回 → 4）；
- 签字里的指纹码与清单一致（否则 4）；
- 清单里的文件当前指纹与清单一致（否则 3，即"签后文件已变，签字作废"）。

全部通过为 0。按任务核对时，任一个包不通过即取最严重的退出码，并逐包列出结果。〔v0.2〕严重程度从高到低为 **5 ＞ 3 ＞ 4**：记录损坏最重；签后改件（签过的东西被动了）比尚未签字（正常的待办）更需要关注。包编号格式不合法或包不存在 → 1。

### 5.5 `tl check --task <任务编号> [--json]`

核对以下几项：
- 进度卡：字段齐全、取值合法；
- 假设日志：每行格式合法，定"低"时附了固定理由；
- 交接卡：`forms/` 下所有 `07_交接卡*.md` 的六个栏目都不为空（D-206④ 交接卡字段校验）；
- 编号：任务编号与包编号符合第 3 节格式，包编号中的任务部分与所在任务一致〔v0.2〕。
- 〔v0.2〕任务目录下还没有 `assumptions.jsonl` 或 `forms/` 时视为合法（该步尚未产生这些记录）。
- 交接卡栏目按表格第一列文字的开头识别（本步、产出、检查结果、未决事项、下一步、令牌移交），填写内容在第二列；整行缺失、只有空白（含全角空格）都算空。

通过为 0；有问题为 2，逐条列出文件、位置和原因。

## 6. 与验收用例的对应（门1 确认单第二节）

| 验收用例 | 由哪个子命令的哪条规则保证 |
| :-- | :-- |
| 伪造签字判无效 | `verify`：指纹码核对、链式校验、同包唯一 |
| 签后改件即作废 | `verify` 与 `sign` 第 1 步：重新计算指纹 |
| 你能签（电脑、手机） | `sign` 追加写入，加上做法 A 批准框（人工实测） |
| 不经批准写不进签字目录 | 做法 A 与 Codex 沙箱（人工实测，不由 `tl` 保证） |
| 交接卡字段校验 | `check` |
| 贯通用例中的"推进前核对" | `verify --task` |
